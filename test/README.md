# テスト

```
npm test          # node --test test/*.test.mjs
```

Node 24 以降が必要です。依存パッケージはありません。

## 仕組み

`index.html` はビルドを持たない単一ファイルなので、テストは
`<script id="core">` の中身を取り出して関数として評価します（`extract.mjs`）。
`core` は DOM に触れない純ロジックで、`ui` が DOM イベントを担当します。
この分担は `extract.mjs` が起動時に検査するので、`core` に `document` などが
混入するとテストが理由付きで落ちます。

フィクスチャは JPEG のバイト列を JS で組み立てます（`fixtures.mjs`）。
`parseJpeg` はヘッダしか読まないため、エントロピー符号化データが妥当である
必要がありません。おかげでバイナリをコミットせずに済み、壊れたセグメント長や
12bit、分割 ICC のように実ファイルでは作りにくいケースも表現できます。

## なぜ core.mjs に分離して import しないのか

素直に `core.mjs` を作って `import` すれば、`extract.mjs` は丸ごと不要になり、
エディタの補完も型検査も効きます。それでもこの形にしているのは、
**ダウンロードした HTML をダブルクリックして開く使い方を守るため**です。
ES modules は `file://` から読めない（CORS で弾かれる）ので、
`<script type="module" src="./core.mjs">` にした時点でこの経路が壊れます。
アップロードせずローカルで完結することがこのツールの value なので、
そこを優先しました。

裏を返すと、**常に HTTP で配信すると決めたならこの制約は消えます**。
その場合は `core.mjs` へ分離するほうが素直です。

現状で払っているコストは次のとおりです。

- エディタ・LSP が HTML 内の JS を追えない（補完・定義ジャンプが効かない）
- `tsc --checkJs` による型検査を後から足せない
- 正規表現による抽出層が存在すること自体

スタックトレースについては、評価するソースに行を詰めて `sourceURL` を
付けることで `index.html` の実際の行番号を指すようにしてあります。
この対応関係は `extract.test.mjs` が検証しているので、狂えば気づけます。

## 注意

`pdf.test.mjs` の EXIF Orientation の期待値（`EXPECTED`）は、
2026-09-16 に mutool でレンダリングし ImageMagick で正解画像と比較して
確定したものです（RMSE 0.0027 = JPEG 再圧縮ノイズのみ。向きを取り違えると 0.47）。
現在のテストは外部ツールを使わないため、**この値の正しさ自体は検証していません**。
書き換えるときは同じ手順で実際の描画を確認してください。

`parse.test.mjs` の「短すぎる APP14 は Adobe と判定しない」は意図の記録です。
このガードは深層防御で、外しても公開 API からは差が出ません（理由はテスト内の
コメント参照）。この 1 件だけはミューテーションで殺せないことを確認済みです。
